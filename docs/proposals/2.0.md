# FieldTest 2.0 proposal

Status: proposed, 2026-09-29. Written as the package's product owner, from its first production use (the tos.watch shape check) and from running 1.0.2 against 326 real `SKILL.md` files.

## In one line

2.0 validates a Markdown document as two kinds of data: the frontmatter, which is already structured YAML, and the body, which FieldTest turns into a fixed outline object. Any Standard Schema library can check both. The first built-in preset validates agent skills.

## Step 0: security patch, before any 2.0 work (1.0.3)

`parseMarkdown` passes input to `gray-matter` with its default engines. Front matter that opens with `---js` is run through `eval`. Verified on 1.0.2:

```js
parseMarkdown('---js\n{ name: (globalThis.PWNED = "ran", "x") }\n---\nbody');
globalThis.PWNED; // "ran"
```

Anyone validating Markdown they didn't write (a downloaded skill pack, user-submitted content, a CI check on a fork's PR) runs its code. Fix: pass `engines` that throw for `js` and `javascript` (or accept only YAML), and add one regression test with the payload above. Publish it as 1.0.3 and note it in the changelog. 2.0 removes the problem for good by dropping gray-matter (below).

## Evidence

**tos.watch** (`shape/check.mjs`) validates computed per-version profiles against a zod schema built from each document's own history. FieldTest cost 0.16 s of a 33 s run, so speed isn't a concern. The rough edges it hit:

1. The README calls `loadUserSchema`, which `@fieldtest/core` doesn't export. A zod schema passed directly to `validateWithSchema` works.
2. `validateWithSchema` returns `T | FailureResult`. The caller has to check for `.issues` on something that might itself be the value.
3. `@fieldtest/core` re-exports all of `@fieldtest/validation-lib`, which brings in `commander` and pins `zod ^3.22.4`. zod is now at 4.6.

**Agent skills.** I ran 1.0.2 (`parseMarkdown` + `validateWithSchema` + zod) against every `SKILL.md` on the maintainer's machine: 326 files across personal, vault, and repo skill folders. The checks were the [Agent Skills spec](https://agentskills.io/specification) frontmatter rules, the Claude Code frontmatter reference, and simple body checks:

| Finding | Files | What it means |
|---|---|---|
| YAML that doesn't parse (unquoted `: ` inside `description`) | 21 | `parseMarkdown` **throws**; a batch run dies on the first one unless the caller wraps every call. At least one of these files is loaded by Claude Code today, so a strict parser is stricter than the host. |
| `user-invokable` (misspelled; the field is `user-invocable`) | 249 | Claude Code ignores the unknown key, so the intended setting silently doesn't apply. All of them came from one generator (Forage's skill templates) copied into 9 repos. |
| `metadata` values that are arrays or booleans | 248 | The spec says string to string. Claude Code keeps any map, and claude.ai uploads follow the spec. It's valid in one host and invalid in another. |
| `allowed-tools` as a YAML list | 2 | Valid in Claude Code, invalid in the spec (space-separated string). |
| Missing `name`/`description`, or `name` not matching its folder | 5 | Real errors under the spec. |
| Same skill name, different content across copies | 15 names | Copies of one skill have drifted apart. No single-file validator can see this. |
| Body over 500 lines or about 5,000 tokens; relative links that don't resolve | 2; 4; 3 | Spec guidance on size, plus broken links. |

A reference validator already exists (`skills-ref validate`, from the spec's authors). It checks one skill's frontmatter against the spec. FieldTest shouldn't copy it. What it can add: host profiles (spec vs Claude Code), body and link checks, drift across a tree of skills, a JS library for CI and hooks, and structured issues with file and line.

## What 2.0 is

### 1. A small core with no schema-library dependency (breaking)

- `@fieldtest/core` depends on the Standard Schema types (`@standard-schema/spec` 1.x) and a YAML parser, nothing else. It no longer re-exports `validation-lib`, `z`, `validate`, or `formatZodError`.
- zod is no longer a dependency of core. Packages that ship zod-written presets list it as a **peer dependency**, `zod ^3.25 || ^4` (3.25 and later can also import v4 from `zod/v4`). Every schema library that implements Standard Schema (zod 3.24+, zod 4, valibot, arktype) works with core as it is.
- The 1.x consumers are all the maintainer's own: four repos import `parseMarkdown, validate, formatZodError, z` from core, and tos.watch imports `validateWithSchema, z`. Migration is `import { z } from "zod"` plus the `check` call below. Write it down once in `MIGRATING.md`.

### 2. One result shape (breaking)

```ts
check(schema, data): Promise<Result<T>>
type Result<T> = { ok: true; value: T } | { ok: false; issues: Issue[] }
type Issue = { message: string; path: (string | number)[]; source?: "frontmatter" | "body" | "parse" | "tree"; line?: number; file?: string; rule?: string; severity: "error" | "warn" }
```

`validateWithSchema` is removed rather than changed. The return shape changes, and tos.watch calls it from plain `.mjs` where no type checker would catch a silent change. A renamed function fails loudly instead. `throwOnError` stays as an option on `check`. `formatIssues(issues)` replaces `formatZodError` and works with any schema library.

### 3. Documents: frontmatter plus body outline (new, the core idea)

The frontmatter is structured data already. The body isn't free text either: Markdown gives every document the same few elements, so FieldTest can build them into a fixed shape once, and any schema can check that shape.

```ts
parseDocument(source, { path? }): Result<Document>   // YAML errors come back as issues, never a throw
type Document = { path?; raw; frontmatter: unknown; body: string; outline: Outline }
type Outline = {
  lines: number; approxTokens: number;
  headings: { depth: 1-6; text: string; line: number }[];
  codeBlocks: { lang?: string; line: number }[];
  links: { href: string; text: string; line: number; relative: boolean }[];
  lists: number; tables: number;
}
checkDocument(doc, { frontmatter?: Schema; outline?: Schema; rules?: Rule[] }): Promise<Result<Document>>
```

- "Has a `## Usage` section", "no H1 other than the title", "under 500 lines", and "every code block names a language" become ordinary schema refinements on `outline`, written in whatever library the user already knows.
- `rules` covers checks that need the file system, like "relative links resolve". A rule is a function `(doc, ctx) => Issue[]`. Keep the built-in set small.
- Issues carry `source` and `line`, so an editor, CI annotation, or hook can point at the exact place.
- Parse with a small, maintained YAML library (`yaml` or `js-yaml` 4 with the core schema) instead of gray-matter. That closes step 0's `eval` path for good. A YAML error becomes a `parse` issue with the line and, for the common unquoted-colon case, a suggested fix ("quote this value").

### 4. Agent skills preset (new, the first reason to install 2.0)

In `@fieldtest/registry`:

- `skills.spec`: the Agent Skills spec. `name` 1–64 characters, lowercase letters, digits, and single hyphens, and matching its folder. `description` 1–1024 characters. `compatibility` up to 500 characters. `metadata` string to string. `allowed-tools` as a string. Body under 500 lines, with a warning above about 5,000 tokens. Relative references resolve and sit at most one level deep.
- `skills.claudeCode`: the Claude Code superset. The extra keys are `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `disallowed-tools`, `model`, `effort`, `context`, `agent`, `background`, `hooks`, `paths`, and `shell`. It accepts both list and string forms where Claude Code does, and applies the 1,536-character cap on `description` plus `when_to_use`. An **unknown key is a warning with a suggestion** (`user-invokable` → did you mean `user-invocable`?), which is the check that would have caught the 249.
- `checkSkillTree(roots, { profile })` finds every `SKILL.md`, checks each one, and adds cross-file issues: duplicate names, and copies with the same name whose content differs. The CLI is `fieldtest skills <dir...> [--profile spec|claude-code] [--json]`, and it exits non-zero on errors so it works in CI and pre-commit hooks.
- Keep the host field lists in one data file with the date and source URL. Host fields change between releases.

### 5. Package surface

2.0 publishes three packages: `@fieldtest/core` (parse, outline, check, issues, types), `@fieldtest/registry` (presets, including skills and the existing Obsidian Bases schema), and `@fieldtest/cli` (the `fieldtest` binary; commander moves here). `validate`, `validation-lib`, and `shared` get a final 1.x release and `npm deprecate` pointing to core. `doc-ref`, `openapi`, and `playwright` stay on their own versions and only move to the new peer range.

## Not in 2.0

- A history-based bounds helper for data validation (`historyBounds(values, { low, high })`, from tos.watch). It's useful and it isn't breaking, so it can ship in 2.1 once a second consumer needs it.
- A lenient YAML mode that copies each host's parser. Report the error with a fix; don't guess what the host would have accepted.
- Semantic linting of descriptions ("is this a good trigger phrase"). That's a model's job, not a validator's.

## Order of work

1. 1.0.3 security patch (step 0).
2. Core: `check`, `Issue`, `formatIssues`, the YAML parser switch, and `parseDocument` returning parse issues. Drop the re-exports.
3. Outline plus `checkDocument`, tested on this repo's own docs and the tos.watch alert files (`alerts/*.md`), which were already the next planned test there.
4. Skills preset plus `checkSkillTree` plus the CLI. Acceptance: on the 326-file corpus it reports the 21 parse errors without crashing, the 249 misspelled keys, and the 15 drifted names, and it matches `skills-ref` on every spec-only error.
5. Migrate the six 1.x consumers, write `MIGRATING.md`, fix the README (`loadUserSchema`), and publish 2.0.0.

## Decisions for the maintainer

- Remove `validateWithSchema`, or keep it as a deprecated alias for 2.x? This proposal removes it, because every consumer is the maintainer's own.
- The name `@fieldtest/cli` vs a bin in `registry`. This proposal uses a separate package so core and registry stay free of CLI dependencies.
